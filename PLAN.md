# План развития IT Career Navigator

## Итоговая цель

Название дипломного проекта: «Интеллектуальная система подбора и планирования образовательной траектории на основе требований IT-вакансий».

Необязательный дополнительный компонент — встроенный интеллектуальный чат-помощник по навигации и использованию системы. Он локально распознаёт типовые вопросы, перефразировки и небольшие опечатки, возвращает заранее подготовленные инструкции и ссылки на доступные разделы. Помощник использует самостоятельно обучаемый ML-классификатор без внешнего LLM API и не является универсальным собеседником.

Дополнительный сценарий — подбор подходящих вакансий по реальному профилю пользователя и подготовка персонализированных сопроводительных писем. Система объясняет рекомендации, показывает недостающие навыки и сохраняет историю подборов и писем. Пользователь редактирует и копирует письмо для самостоятельного отклика. Первоначальный сценарий «анализ рынка → skill gap → образовательная траектория» сохраняется и использует общий с новым модулем каталог вакансий и навыков.

Собрать демонстрируемую дипломную систему: пользователь регистрируется, задаёт целевое IT-направление и уровень, указывает навыки, запускает анализ импортированных вакансий и получает статистику рынка, skill gap и персональный roadmap. План следует концепции проекта: импорт JSON/CSV, OpenAI-совместимый LLM API с fallback, Jinja-интерфейс, PostgreSQL, Celery, RabbitMQ, Redis и Docker Compose. :codex-file-citation{path="C:\Users\Ильгар\Desktop\Kontseptsia_diplomnogo_proekta_IT_vakansii.docx" purpose="source" artifact_kind="document"}

## Этап 5А — Персональный подбор вакансий и сопроводительные письма

Модуль развивать последовательно: профиль → подбор → объяснения → письма → расширение интерфейса. Уже реализованы расширенный профиль, условия работы в вакансиях, подбор по сохранённым требованиям, объяснения, история и Jinja-страницы подбора. Генерация писем остаётся запланированной; подбор пока выполняется в HTTP-запросе без автоматического вызова LLM, а вакансии без разобранных требований показываются без оценки.

### Поиск и оценка соответствия

- В первой версии искать только среди импортированных вакансий. Фильтры: желаемая должность, направление, уровень и рабочие предпочтения.
- Название должности искать в заголовке без учёта регистра; навыки сопоставлять по каноническим ID после нормализации псевдонимов.
- Совпадение навыков считать как долю выполненных требований с весами: обязательный навык — 2, дополнительный — 1.
- При известных данных об опыте итоговый балл равен 80% совпадения навыков + 20% соответствия стажа. Соответствие стажа — отношение имеющегося стажа к требуемому, максимум 100%; при явном отсутствии требований к стажу этот компонент равен 100%.
- Если опыт неизвестен хотя бы с одной стороны, считать балл только по навыкам с отметкой «опыт не оценён». Вакансии без извлечённых требований показывать отдельно, без искусственного процента.
- Рабочие предпочтения использовать как фильтры. Включение вакансий с неизвестными условиями управляется отдельным переключателем, включённым по умолчанию.
- Сортировать по убыванию балла, затем по дате публикации; вакансии без даты помещать после датированных при равных баллах. Балл означает соответствие указанным требованиям, а не вероятность трудоустройства.
- Проекты использовать в объяснениях и письмах, не приравнивая их к коммерческому стажу. Сохранять снимки исходных данных и результаты, чтобы редактирование профиля не переписывало историю.
- Переиспользовать принцип сравнения навыков из roadmap. Переход к образовательной траектории ведёт в существующий сценарий анализа; отдельную систему roadmap для подбора не создавать.

### Генерация писем

- Передавать LLM выбранную вакансию и только сохранённые пользователем сведения, необходимые для письма. Пароли, токены и ненужные персональные данные не передавать.
- Генерировать русский текст примерно на 150–250 слов. Пользователь просматривает, редактирует, сохраняет и копирует письмо для самостоятельного отклика.
- Запрашивать структурированные блоки письма со ссылками на факты профиля. Проверять, что утверждения о навыках, организациях, должностях, сроках и числовых достижениях подтверждены данными пользователя; неподтверждённый результат не сохранять как успешное письмо.
- Рассматривать текст вакансии как данные: инструкции внутри описания не должны менять правила генерации. Не ограничивать защиту одной просьбой к модели «не выдумывать».
- Проверка утверждений снижает риск выдумок, но не даёт абсолютной гарантии; сохранить обязательный просмотр пользователем перед копированием и ручную оценку качества на тестовых примерах.
- При недоступности LLM показывать понятную ошибку и возможность повтора; не терять подборы и ранее сохранённые тексты. Словарный fallback используется для извлечения требований, а не для имитации сгенерированного письма.
- Повторная генерация создаёт отдельный черновик и сохраняет ручные правки предыдущего. Автоматическую отправку откликов не реализовывать.

### Архитектура и API

- Организовать цепочку обычными сервисами Python: поиск кандидатов → извлечение отсутствующих требований → сопоставление → сохранение → генерация выбранного письма. Переиспользовать существующий стек FastAPI, SQLAlchemy, PostgreSQL, Pydantic и OpenAI-совместимый адаптер.
- LangChain/LangGraph рассмотреть как последующее развитие при появлении сложных ветвлений и возобновляемых процессов. В первую версию не добавлять эти зависимости: текущая последовательность реализуется существующими средствами.
- API использует JWT, Jinja-страницы — существующую сессию; обе точки входа вызывают общие сервисы. ID владельца берётся из авторизации, доступ к чужим профилям, подборам и письмам запрещён.

## Этап 5Б — Интеллектуальный чат-помощник по навигации и использованию системы

Самостоятельный необязательный модуль. Все пункты этапа являются запланированными; его отсутствие не блокирует анализ вакансий, сопоставление навыков, образовательные траектории, подбор вакансий и подготовку писем.

### Назначение и пользовательские сценарии

- Помогать пользователю найти нужный раздел и понять порядок действий. Самостоятельно не запускать анализы, не изменять профиль и не отправлять отклики.
- Распознавать намерения: изменение профиля, опыта и проектов; добавление и изменение навыков; выбор направления и уровня; создание и запуск анализа; просмотр результатов и объяснение skill gap; построение и использование roadmap; поиск подходящих вакансий; подготовка сопроводительного письма; справка о возможностях помощника.
- Поддерживать вопросы вроде «Как провести анализ навыков?», «Какие технологии мне изучить?», «Как изменить профиль?» и их разговорные перефразировки с небольшими опечатками.
- На вопрос о выборе специальности объяснять существующий выбор направления в профиле, не обещая персональную профориентационную диагностику.
- При неизвестном, постороннем или неоднозначном запросе возвращать fallback: «Не удалось понять вопрос. Могу помочь с профилем, анализом навыков или образовательной траекторией», предлагая доступные темы.
- Подготовленные ответы должны соответствовать реально работающим функциям. До завершения соответствующих частей этапа 5А сообщать, что подбор вакансий и письма находятся в разработке, без несуществующих ссылок. При реализации этих функций обновить ответы и переходы помощника как часть критериев готовности этапа 5А.

### Данные и обучение классификатора

- Использовать архитектурные идеи DiskWizard, перечисленные в концепции: Python, scikit-learn, символьные TF-IDF-признаки, LinearSVC, нормализация, проверка похожести и подготовленные ответы. Перенос кода учебного проекта не является условием реализации.
- Подготовить версионируемый набор намерений, обучающих фраз, ответов и идентификаторов разделов. Для каждого намерения — минимум 30 обучающих примеров с разными формулировками, разговорными выражениями и характерными опечатками.
- Отдельно подготовить минимум 10 валидационных и 10 тестовых фраз на намерение; для проверки отказа — минимум по 30 посторонних и неоднозначных запросов в валидационной и тестовой выборках.
- Разделять данные по семействам формулировок: варианты одной фразы и её искусственные опечатки не должны попадать одновременно в обучение и тест. Проверять отсутствие дубликатов после нормализации.
- Нормализовать регистр, пробелы, Unicode и `ё/е`, сохраняя значимые символы технических названий. Отдельный сервис исправления орфографии не добавлять.
- Обучать `TfidfVectorizer(analyzer="char_wb", ngram_range=(3, 5))` и `LinearSVC`. Опечатки обрабатывать за счёт символьных признаков, дополнительно проверяя косинусную похожесть запроса на обучающие фразы предсказанного намерения.
- Принимать решение по сочетанию оценки классификатора, разницы между двумя лучшими классами и похожести фраз. Оценку LinearSVC не называть вероятностью. Нулевой вектор запроса направлять в fallback.
- Пороги отказа подбирать на валидационной выборке и фиксировать вместе с моделью. Финальный тест не использовать для настройки; пользовательские сообщения автоматически в обучение не включать.
- Предусмотреть отдельную команду обучения и отчёт: метрики по намерениям, матрица ошибок, доля принятых запросов и качество fallback.

### Архитектура, обучение и загрузка

- Разместить небольшой модуль внутри существующего FastAPI-приложения: нормализация → векторизация → классификация → проверка уверенности и похожести → выбор подготовленного ответа.
- Использовать Python и scikit-learn, сохранять артефакт стандартным для этого стека механизмом сериализации. При реализации проверить совместимость зависимостей с используемым Python 3.14.
- Сохранять векторизатор, классификатор, пороги, версию набора данных и версии библиотек. Загружать только доверенный локальный артефакт, один раз на процесс. Обучение внутри HTTP-запроса не выполнять.
- Не использовать для помощника существующий LLM-адаптер, внешние модели, векторную БД, LangChain/LangGraph или отдельный микросервис. Классификатор обучается на подготовленных примерах; текст ответа выбирается из справочника.
- При отсутствующей или несовместимой модели отключать только помощника. Приложение должно запускаться, основные функции продолжают работать; виджет показывает сообщение о недоступности и статические ссылки на основные разделы.

### FastAPI и Jinja-интерфейс

- Запланировать `POST /assistant/message`: запрос содержит непустую строку `message` до 1000 символов; ответ — `intent`, подготовленный текст `answer`, список `actions` и признак `fallback`. Для fallback без распознанного намерения `intent` равен `null`.
- Каждое действие содержит идентификатор раздела, подпись и разрешённую внутреннюю ссылку. Ссылки формировать только из справочника, не из пользовательского текста.
- Endpoint первой версии публичный и не использует персональные данные; он выдаёт справочную информацию. Переходы в защищённые разделы сохраняют существующие требования авторизации.
- Для низкой уверенности возвращать обычный ответ с `fallback=true`; при недоступной модели — `503` с безопасным сообщением и статическими действиями. Невалидный ввод отклонять через стандартную валидацию API.
- Виджет на Jinja2 + HTML/CSS/JavaScript показывает сообщения как текст, без исполнения HTML, поддерживает отправку, готовые темы и ссылки-переходы. Диалог хранится только в памяти открытой страницы; новые таблицы истории чата не нужны.
- Использовать существующие `/profile`, якоря профиля и `/analyses`. Для построения и открытия roadmap направлять в список анализов, поскольку конкретный roadmap имеет собственный ID. Не генерировать несуществующие ссылки на ещё не реализованные функции.

### Порядок разработки и тестирования

1. Зафиксировать намерения и подготовленные ответы по реально доступным страницам.
2. Разметить и разделить обучающие, валидационные и независимые тестовые данные.
3. Обучить классификатор, настроить fallback на валидации, сохранить артефакт и отчёт.
4. Реализовать загрузку модели и справочный API внутри приложения.
5. Подключить виджет, проверить ссылки, адаптивность и обработку ошибок.

Проверять типовые вопросы, новые перефразировки и опечатки; путаницу между анализом, результатами, roadmap и подбором вакансий; посторонние, бессмысленные и неоднозначные сообщения; пустой и слишком длинный ввод; безопасное отображение текста; существование всех ссылок; отсутствие внешних вызовов; запуск приложения и работу основных сценариев при недоступном помощнике.

**Критерии готовности:** на независимом тесте не менее 90% правильных ответов на типовые вопросы и перефразировки, не менее 80% на отдельной группе небольших опечаток и не менее 90% корректных fallback на посторонних и неоднозначных запросах. Fallback на поддерживаемый вопрос считать ошибкой при оценке первых двух показателей. Публиковать размеры выборок и результаты по каждому намерению; при недостижении целей дорабатывать данные и пороги без настройки по финальному тесту. Помощник работает локально без внешнего API, выдаёт проверенные инструкции и действующие переходы и не мешает основным функциям сайта.

## Этап 6 — Фоновые задачи и контейнеризация

- Добавить Celery worker: импорт, LLM-извлечение и расчёт анализа выполняются вне HTTP-запроса.
- Использовать RabbitMQ как broker, Redis для состояния задач/кэша, PostgreSQL как основное хранилище.
- В `docker-compose.yml` определить сервисы `app`, `worker`, `postgres`, `rabbitmq`, `redis`; добавить healthchecks, том PostgreSQL и единый `.env`.
- Интерфейс должен показывать статусы `queued`, `running`, `completed`, `failed`; при ошибке — безопасное сообщение и возможность повторить анализ.
- После подключения Celery вынести также подбор вакансий и генерацию писем в worker с теми же статусами. Результаты и историю хранить в PostgreSQL; ошибки задач не должны уничтожать ранее сохранённые результаты и письма.

**Готово, когда:** `docker compose up --build` поднимает весь стенд, а анализ продолжает выполняться worker-процессом после возврата HTTP-ответа.

## Принятые допущения

- В MVP вакансии поступают из подготовленного JSON/CSV; внешние API и парсинг сайтов остаются возможным следующим этапом.
- LLM подключается через OpenAI-совместимый API. Извлечение требований остаётся работоспособным в режиме fallback; генерация писем требует доступной LLM и при её ошибке возвращает понятное сообщение.
- Один пользователь хранит одно актуальное целевое направление и уровень; история анализов сохраняется отдельно.
- Внутренний API-ключ обслуживает импорт и управление справочником; пользовательский API защищён JWT, браузерные страницы используют существующую сессию. Владение данными проверяется в обоих случаях.
- Первая версия персонального подбора использует импортированные вакансии. Подключение одного внешнего API — отдельный следующий этап через адаптер к существующему импорту с дедупликацией по `source + external_id`; конкретный источник выбрать при планировании этого этапа.
- Данные профиля считаются заявленными пользователем; система не подтверждает достоверность указанного опыта и достижений.
- Автоотклики, новая инфраструктура и обязательное подключение LangChain/LangGraph в объём нового модуля не входят.
- Чат-помощник этапа 5Б — необязательный локальный ML-компонент для справки и навигации. Он использует обучаемый TF-IDF + LinearSVC-классификатор и подготовленные ответы, не обращается к внешнему LLM API и не зависит от доступности LLM для остальных функций проекта.
- Модель помощника обучается отдельной командой на подготовленном наборе данных, а приложение загружает готовый доверенный артефакт. Автоматическое обучение на сообщениях пользователей, персональные рекомендации из чата и хранение истории чата в БД в первую версию не входят.
