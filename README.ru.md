# IT Career Navigator

[English](README.md) | [Русский](README.ru.md)

## Назначение проекта

**IT Career Navigator** — серверная часть системы поддержки карьерного развития в IT. Проект создаётся как дипломная работа. Его целевая задача — помочь пользователю сопоставить собственный профиль навыков с требованиями рынка вакансий и получить персонализированный план развития.

Текущая версия реализует базовый слой системы: учётные записи, профиль пользователя, каталог навыков, JWT-аутентификацию и внутренний API-ключ. Импорт вакансий, LLM-анализ, статистика рынка, skill gap, roadmap и пользовательский веб-интерфейс пока не реализованы; они описаны в [PLAN.md](PLAN.md).

## Актуальность

Требования к IT-специалистам меняются быстро, а вакансии используют неодинаковые формулировки одних и тех же технологий. Система должна собрать требования из вакансий, нормализовать навыки и показать пользователю, какие компетенции наиболее важны для выбранного направления. Текущий backend является основой для такой системы.

## Цель и задачи разработки

### Цель

Создать демонстрируемую систему навигации по IT-карьере: от регистрации и заполнения навыков до последующего анализа вакансий и формирования персонального roadmap.

### Реализованные задачи

- создано асинхронное FastAPI-приложение;
- настроено подключение к базе данных через async SQLAlchemy;
- реализованы регистрация и вход пользователя;
- реализованы хеширование пароля и выдача JWT;
- защищены личные действия пользователя с помощью Bearer-токена;
- реализовано добавление и удаление навыков текущего пользователя;
- создан внутренний API для управления каталогом навыков с отдельным API-ключом;
- добавлены API-тесты пользовательских и внутренних сценариев.

### Планируемые задачи

План развития находится в [PLAN.md](PLAN.md). В него входят переход на PostgreSQL и Alembic, импорт JSON/CSV вакансий, нормализация синонимов навыков, OpenAI-совместимый LLM-адаптер с fallback, расчёт skill gap и roadmap, Jinja-интерфейс, фоновые задачи Celery, RabbitMQ, Redis и Docker Compose.

## Архитектура

Приложение организовано по слоям:

```text
HTTP client / Swagger
        │
        ▼
FastAPI routers
  ├── users.py      — пользовательские операции
  └── internal.py   — доверенные внутренние операции
        │
        ▼
Pydantic schemas + dependencies
  ├── auth.py       — JWT, пароль, API-ключ
  └── database.py   — сессия БД
        │
        ▼
SQLAlchemy models → SQLite (текущая реализация)
```

В `main.py` используется `lifespan`: при запуске вызывается `Base.metadata.create_all()`, создающий таблицы текущих моделей в настроенной базе. Миграции Alembic в проект ещё не добавлены.

## Модели данных и связи

В текущей версии определены три SQLAlchemy-модели.

| Модель | Назначение | Основные поля |
| --- | --- | --- |
| `Person` | Учётная запись и профиль пользователя. | `id`, `name`, `surname`, `age`, `email`, `phone`, `password` |
| `Skills` | Общий справочник навыков. | `id`, `name` |
| `PersonSkills` | Таблица связи пользователя и навыка. | `id`, `person_id`, `skill_id` |

Связь между пользователем и навыками реализована как many-to-many через промежуточную сущность:

```text
Person 1 ──── * PersonSkills * ──── 1 Skills
```

`Person.email` и `Skills.name` имеют ограничение уникальности. В `PersonSkills` хранятся внешние ключи на обе сущности; для них задано каскадное удаление на уровне определения внешнего ключа.

### Pydantic-схемы

- `PersonCreate` — данные регистрации, включая пароль.
- `PersonUpdate` — частично обновляемый профиль.
- `PersonResponse` — ответ с профилем и списком навыков; пароль в него не включается.
- `SkillCreate` и `SkillResponse` — входная и выходная схемы навыка.

Схемы ответов используют `ConfigDict(from_attributes=True)`, поэтому Pydantic может формировать ответ из ORM-объектов SQLAlchemy.

## Аутентификация и разграничение доступа

### JWT для пользовательских операций

Пароль сохраняется не в открытом виде: `pwdlib` формирует Argon2-хеш. При успешном входе создаётся JWT с идентификатором пользователя в claim `sub` и временем истечения `exp`.

`OAuth2PasswordBearer` извлекает токен из заголовка:

```http
Authorization: Bearer <access_token>
```

Dependency `get_current_user` проверяет подпись и срок действия токена, извлекает `sub` и передаёт ID текущего пользователя в защищённый endpoint. Поэтому личные операции не принимают ID пользователя от клиента: они используют идентификатор из JWT.

### Внутренний API-ключ

Операции с внутренним каталогом навыков не используют JWT. Они защищены dependency `InternalAPIKey`, которая читает заголовок:

```http
X-Internal-API-Key: <internal_api_key>
```

Ключ сравнивается через `secrets.compare_digest`, что предназначено для безопасного сравнения секретных строк. Если ключ отсутствует или не совпадает, API возвращает `401`; если ключ не настроен — `503`.

## API

Swagger UI после запуска доступен по адресу `http://127.0.0.1:8000/docs`.

### Пользовательские endpoints

| Метод | Путь | Доступ | Назначение |
| --- | --- | --- | --- |
| `POST` | `/users/create_user` | Открытый | Регистрация пользователя. |
| `POST` | `/users/login` | Открытый | Вход по OAuth2 password flow. Поле формы `username` содержит email. |
| `GET` | `/users/me` | JWT | Получение профиля текущего пользователя. |
| `PATCH` | `/users/update_user` | JWT | Изменение профиля текущего пользователя. |
| `DELETE` | `/users/delete_user` | JWT | Удаление текущего пользователя. |
| `POST` | `/users/add_skills` | JWT | Добавление списка навыков текущему пользователю. |
| `DELETE` | `/users/delete_skills` | JWT | Удаление списка навыков текущего пользователя. |
| `GET` | `/users/{user_id}` | Открытый | Временный демонстрационный endpoint: возвращает фиктивное имя, не получает пользователя из БД. |

### Внутренние endpoints

| Метод | Путь | Доступ | Назначение |
| --- | --- | --- | --- |
| `POST` | `/internal/create_skills` | API-ключ | Создание навыка в общем справочнике. |
| `DELETE` | `/internal/delete_skills` | API-ключ | Удаление всех навыков из общего справочника. Использовать только в доверенном административном контексте. |

### Пример входа

Endpoint `/users/login` принимает не JSON, а form-data `application/x-www-form-urlencoded`:

```text
username=user@example.com
password=your-password
```

В ответ возвращаются `access_token` и `token_type: bearer`.

## Установка и запуск

### Предварительные требования

- Python 3.14 или новее;
- установленный `uv`.

### Установка зависимостей

```bash
uv sync
```

### Настройка окружения

Создай `.env` на основе шаблона:

```powershell
Copy-Item .env.example .env
```

Пример значений для локальной разработки:

```dotenv
db_url=sqlite+aiosqlite:///./it_career_navigator.db
secret_key=replace-with-a-long-random-secret-of-at-least-32-characters
algorithm=HS256
access_token_expire_minutes=30
internal_api_key=replace-with-a-separate-internal-key
```

| Переменная | Назначение |
| --- | --- |
| `db_url` | URL базы данных SQLAlchemy. Сейчас применяется async SQLite URL. |
| `secret_key` | Секрет подписи JWT. Его нельзя публиковать. |
| `algorithm` | Алгоритм JWT; значение по умолчанию — `HS256`. |
| `access_token_expire_minutes` | Время действия access token в минутах; по умолчанию `30`. |
| `internal_api_key` | Секрет для внутренних endpoints. |

### Запуск приложения

Из корня репозитория:

```bash
uv run fastapi dev src/it_career_navigator/main.py
```

Сервис запускается на `http://127.0.0.1:8000`, Swagger UI — на `http://127.0.0.1:8000/docs`.

## Тестирование

Пользовательские сценарии:

```bash
uv run pytest src/it_career_navigator/tests/test_user.py -v
```

Внутренний API:

```bash
uv run pytest src/it_career_navigator/tests/test_internal.py -v
```

Тестовая конфигурация до импорта приложения устанавливает отдельные `DB_URL`, `SECRET_KEY` и `INTERNAL_API_KEY`. HTTP-запросы выполняются через `httpx.AsyncClient` и `ASGITransport`, без отдельного запущенного сервера.

### Текущее ограничение запуска всей коллекции

В `src/it_career_navigator/tests/conftest.py` сейчас объявлено `pytest_plugins = ["anyio"]`. В pytest 9 такое объявление во вложенном `conftest.py` может приводить к ошибке при выполнении команды `uv run pytest -v` из корня проекта: его требуется перенести в корневой `conftest.py` или удалить, так как AnyIO уже подключён. Поэтому в текущей документации приведены проверенные команды запуска тестовых файлов по отдельности.

## Перспективы развития

Согласно [PLAN.md](PLAN.md), дальнейшая разработка разделена на этапы:

1. Уточнение контрактов API, формата ошибок, тестов и прав доступа.
2. Переход на PostgreSQL, миграции Alembic и расширенная доменная модель.
3. Импорт и нормализация вакансий из JSON/CSV.
4. Извлечение требований вакансий через OpenAI-совместимый LLM API с fallback на ключевые слова.
5. Расчёт статистики рынка, skill gap и приоритетного roadmap.
6. Jinja-интерфейс для пользовательского сценария без Swagger.
7. Celery, RabbitMQ, Redis, Docker Compose и фоновые задачи.
8. Unit-, integration- и демонстрационное тестирование.

## Текущие ограничения и замечания

- Основная БД пока SQLite; PostgreSQL и Alembic не реализованы.
- Нет импорта вакансий, LLM, статистического анализа, skill gap, roadmap, UI, Celery, RabbitMQ, Redis и Docker Compose.
- Таблицы создаются на старте через `Base.metadata.create_all()`, а не миграциями.
- Endpoint `/users/{user_id}` — временная заглушка.
- Внутреннее удаление навыков очищает весь каталог и требует особенно осторожного использования.
- Для полного запуска тестовой коллекции требуется привести расположение `pytest_plugins` в соответствие с требованиями pytest 9.
